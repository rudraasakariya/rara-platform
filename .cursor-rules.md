## Git Workflow

### Branch Naming

- **Feature branches:** `feature/issue-XX-description`
  - Example: `feature/issue-50-main-layout-wrapper`
- **Bug fix branches:** `fix/issue-XX-description`
  - Example: `fix/issue-45-hydration-mismatch`
- Use kebab-case for branch names
- Always include the issue number when working on a GitHub issue

### Commit Messages

Use **Conventional Commits** format:

- `feat:` - New feature
- `fix:` - Bug fix
- `refactor:` - Code refactoring without changing functionality
- `style:` - Code style changes (formatting, missing semicolons, etc.)
- `docs:` - Documentation changes
- `test:` - Adding or updating tests
- `chore:` - Maintenance tasks, dependency updates

**Format:**
```
<type>: <brief description>

<optional detailed description>
```

**Examples:**
```
feat: create MainLayout component with sidebar placeholder

- Add MainLayout component with flex layout structure
- Include sidebar placeholder (hidden on mobile, visible on lg+)
- Set up main content area with consistent max-width and padding
```

```
refactor: remove redundant container classes from dashboard

- Remove container mx-auto p-8 from dashboard page
- MainLayout now handles container spacing and padding
```

### Commit Guidelines

- **Atomic commits:** One logical change per commit
- Each commit should be self-contained and buildable
- Group related changes together
- Separate refactoring from feature changes
- Write clear, descriptive commit messages

### Pull Requests

**CRITICAL RULES:**
- **NEVER create a PR without explicit user approval**
- Always wait for user to request PR creation before using `gh pr create`
- PRs should be created only after user has tested the changes

**PR Requirements:**
- **Title:** Use format: `feat: <description> (Issue #XX)` or `fix: <description> (Issue #XX)`
- **Description:** 
  - Provide a detailed, clear description of what is being fixed or added
  - List all changes made
  - Explain the purpose and impact
  - **Do NOT include a testing section unless specifically requested by the user**
- **Issue linking:** Always include `Fixes #XX` or `Closes #XX` in the PR description
- **Base branch:** Always target `main` unless specified otherwise

**PR Description Template:**
```markdown
## Description
[Detailed description of what is being fixed or added]

## Changes
- [List of specific changes]
- [Another change]

## Features
- [Feature 1]
- [Feature 2]

Fixes #XX
```

## Code Style & Standards

### TypeScript

- Use **strict mode** TypeScript
- Always define explicit types for function parameters and return types
- Use interfaces for object shapes, types for unions/intersections
- Avoid `any` - use `unknown` if type is truly unknown
- Use proper null/undefined handling

### React/Next.js Patterns

#### Client Components
- Use `'use client'` directive at the top of client components
- Place directive before any imports

#### Component Structure
```typescript
'use client';

import { ... } from '...';

interface ComponentProps {
  // Props definition
}

export function ComponentName({ prop1, prop2 }: ComponentProps) {
  // Component logic
  return (
    // JSX
  );
}
```

#### TypeScript Interfaces
- Always define interfaces for component props
- Use descriptive prop names
- Include JSDoc comments for complex props

#### Hooks Usage
- Use custom hooks for reusable logic
- Follow React hooks rules (only call at top level)
- Use proper dependency arrays in useEffect, useMemo, useCallback

### NestJS Patterns

#### Module Structure
- Follow NestJS module pattern: Module → Controller → Service
- Use proper dependency injection
- Keep modules focused and cohesive

#### DTOs
- Always use DTOs for request/response validation
- Use class-validator decorators
- Create separate DTOs for create/update operations when needed

#### Services
- Business logic belongs in services, not controllers
- Controllers should only handle HTTP concerns
- Use proper error handling

### File Naming

- **Files:** Use kebab-case
  - Example: `main-layout.tsx`, `auth-service.ts`
- **Components:** Use PascalCase in file names
  - Example: `MainLayout.tsx`, `AuthService.ts`
- **Directories:** Use kebab-case
  - Example: `layout/`, `auth/`, `user-profile/`

### Import Organization

Order imports as follows:
1. External packages (React, Next.js, etc.)
2. Internal modules (from `@/` aliases)
3. Relative imports (`./`, `../`)

Separate each group with a blank line.

**Example:**
```typescript
import { useState } from 'react';
import Link from 'next/link';

import { useAuth } from '@/contexts/auth-context';
import { Button } from '@/components/ui/button';

import { localUtil } from './utils';
```

## File Structure & Organization

### Frontend Structure

```
frontend/
├── app/                    # Next.js App Router pages
│   ├── layout.tsx         # Root layout
│   ├── page.tsx           # Home page
│   ├── dashboard/         # Feature pages
│   └── globals.css        # Global styles
├── components/            # React components
│   ├── layout/           # Layout components (Navbar, Sidebar, etc.)
│   ├── ui/               # shadcn/ui components
│   ├── auth/             # Auth-related components
│   └── [feature]/        # Feature-specific components
├── lib/                  # Utilities and configurations
│   ├── api/              # API client functions
│   ├── api-client.ts     # Axios instance
│   └── utils.ts          # Utility functions
├── providers/            # React context providers
├── contexts/             # React contexts
├── hooks/               # Custom React hooks
└── public/              # Static assets
```

### Backend Structure

```
backend/
├── src/
│   ├── [module]/         # Feature modules
│   │   ├── [module].module.ts
│   │   ├── [module].controller.ts
│   │   ├── [module].service.ts
│   │   ├── dto/          # Data Transfer Objects
│   │   └── entities/     # Database entities
│   ├── common/           # Shared code
│   ├── database/         # Database configuration
│   └── main.ts           # Application entry point
└── dist/                 # Compiled output
```

### Component Organization

- **Layout components:** `components/layout/`
  - Examples: `navbar.tsx`, `sidebar.tsx`, `main-layout.tsx`
- **UI components:** `components/ui/`
  - shadcn/ui components and reusable UI primitives
- **Feature components:** `components/[feature]/`
  - Components specific to a feature (e.g., `components/students/`)
- **Shared components:** `components/`
  - Components used across multiple features

### Naming Conventions

- **Components:** PascalCase (e.g., `MainLayout`, `UserProfile`)
- **Files:** Match component name (e.g., `MainLayout.tsx`)
- **Hooks:** Start with `use` (e.g., `useAuth`, `useToast`)
- **Utilities:** camelCase (e.g., `formatDate`, `validateEmail`)
- **Constants:** UPPER_SNAKE_CASE (e.g., `API_BASE_URL`)

## Testing Requirements

### When to Write Tests

- **Only write tests when explicitly requested by the user**
- Do not include testing sections in PR descriptions unless asked
- When tests are requested, follow these patterns:

### Testing Patterns (When Implemented)

- **Unit tests:** Test individual functions/components in isolation
- **Integration tests:** Test component interactions
- **E2E tests:** Test complete user flows
- Use appropriate testing libraries (Jest, React Testing Library, etc.)

### Test File Naming

- Test files: `*.test.ts` or `*.spec.ts`
- Co-locate with source files or in `__tests__` directories

```typescript
 * 
 * @param requiredRole - Optional role required to access the route
 */
export function ProtectedRoute({ children, requiredRole }: ProtectedRouteProps) {
  // Implementation
}
```

### README Files

- Create README files for major features or modules
- Include setup instructions, usage examples, and API documentation
- Keep READMEs up to date with code changes

### Inline Documentation

- Document public APIs and interfaces
- Explain non-obvious implementation details
- Note any known limitations or future improvements

### Commit Messages as Documentation

- Clear commit messages serve as project history
- Each commit should tell a story of what changed and why

## Best Practices

### General Guidelines

1. **Keep it simple:** Prefer simple, readable solutions over clever ones
2. **DRY (Don't Repeat Yourself):** Extract reusable code into utilities or components
3. **Single Responsibility:** Each function/component should do one thing well
4. **Consistency:** Follow existing patterns in the codebase
5. **Progressive Enhancement:** Build features incrementally

### Component Design

- Keep components small and focused
- Use composition over inheritance
- Extract logic into custom hooks when reusable
- Prefer props over context when possible

### Error Handling

- Always handle errors gracefully
- Provide meaningful error messages to users
- Log errors appropriately (console in dev, error service in prod)
- Use try-catch for async operations

### Performance

- Use React.memo for expensive components
- Implement proper loading states
- Lazy load routes and heavy components when appropriate
- Optimize images and assets

### Accessibility

- Use semantic HTML elements
- Include proper ARIA labels where needed
- Ensure keyboard navigation works
- Maintain proper color contrast

### Security

- Never commit secrets or API keys
- Validate and sanitize user input
- Use proper authentication and authorization
- Follow security best practices for the framework

### Code Review Checklist

Before considering code complete:
- [ ] Follows naming conventions
- [ ] Has proper TypeScript types
- [ ] Includes error handling
- [ ] Is properly formatted
- [ ] Has no linter errors
- [ ] Follows existing patterns
- [ ] Is tested (if tests were requested)

## Workflow Summary

1. **Start work:** Create branch from `main` using `feature/issue-XX-description` format
2. **Make changes:** Follow code style and structure guidelines
3. **Commit:** Use atomic commits with conventional commit messages
4. **Test:** User will test changes before PR creation
5. **PR:** Wait for user approval before creating PR
6. **PR Description:** Write detailed description, link to issue, no testing section unless asked
7. **Merge:** After review and approval

---

**Remember:** These rules are meant to ensure consistency and quality. When in doubt, follow existing patterns in the codebase and ask for clarification if needed.
